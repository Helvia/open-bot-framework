# Data Model: open-bot-framework

> Domain objects owned and used by this service.
> Standalone DirectLine 3.0 gateway with its own SQL database (`obf`). The driver is chosen
> at runtime from `TYPEORM_CONNECTION` — both `pg` and `mysql2` are installed.
> Full platform schemas: [`docs/domain-model.md`](../../hbf-agentic-framework/docs/domain-model.md)

## Objects This Service Uses

| Object | How | Key fields accessed |
|--------|-----|-------------------|
| — | — | — |

**None.** open-bot-framework reads no hbf-core MongoDB objects, has no dependency on
`@helvia/hbf-core-api`, and makes no HTTP calls to hbf-core. A repo-wide grep for
`hbf-core` / `HBF_CORE` / `hbfCore` in `src/` returns nothing. Auth is entirely local:
`JWT_SECRET`-signed tokens plus a bcrypt `ADMIN_PASSWORD` for the admin login.

The only outbound coupling is to registered bot endpoints (`OpenBot.endpoint`), Redis, and
MinIO/S3.

## Schema Management — read this first

```
synchronize: true          // src/app.module.ts, hardcoded, no env gate
migrations: [__dirname + '/../migrations/*.js']
migrationsRun: TYPEORM_AUTORUN_MIGRATIONS === 'true'
autoLoadEntities: true
dropSchema: false
```

**There is no `migrations/` directory in this repo.** The glob matches zero files, so
`migrationsRun` is inert regardless of how `TYPEORM_AUTORUN_MIGRATIONS` is set, and the
`migration:generate` / `migration:run` / `migration:revert` npm scripts have never produced
a committed migration.

Consequently **the entity classes below are the schema.** TypeORM diffs them against the
live database on every boot and issues whatever DDL closes the gap.

Operational risk of `synchronize: true` in a deployed environment:

- Renaming or removing a property drops the column and its data at the next restart. There
  is no confirmation, no dry run, and no migration to revert.
- Narrowing a column type (e.g. `varchar(255)` → `varchar(64)`) issues an `ALTER` that can
  truncate or fail mid-startup, leaving the service crash-looping.
- Two instances of the service starting concurrently can race on the same DDL.
- There is no schema history, so "what changed and when" is unanswerable after the fact.
- Switching `TYPEORM_CONNECTION` between `postgres` and `mysql` points at a *different*
  database that gets auto-created from the same entities, so a driver flip looks like data
  loss rather than an error.

Adopting migrations means a first migration that captures the current state, then flipping
`synchronize` to `false`. Until then, treat every entity edit as a production DDL change.

### Driver selection

| Context | `TYPEORM_CONNECTION` | Source |
|---------|---------------------|--------|
| Repo default / standalone Docker | `postgres` (`postgres:16-alpine` in `docker-compose.yml`) | `.env`, `docker-compose.yml` |
| HBF local dev | **`mysql`** | generated by the framework's `scripts/local-dev/generate-env.sh` (`TYPEORM_DATABASE=obf`) |

`src/app.module.ts` casts the env value straight to `DataSourceOptions['type']`, so the
service is genuinely driver-agnostic. `ormconfig.ts` (the CLI datasource) does the same but
casts to the literal `'postgres'` for typing convenience — that cast is cosmetic, the value
still comes from `process.env.TYPEORM_CONNECTION`.

Because the driver varies, SQL types below are given per driver where they differ.

## Local Entities

| Entity | Table | DB | Key fields |
|--------|-------|----|-----------|
| OpenBot | `open_bot` | SQL (`obf`), driver per `TYPEORM_CONNECTION` | `id` (uuid PK), `handle` (unique index), `endpoint`, `schemaVersion`, `createdAt`, `updatedAt` |
| OpenBotSecret | `open_bot_secret` | same | `id` (uuid PK), `openBotId` (FK → `open_bot`, CASCADE), `description`, `createdAt`, `expiresAt`, `secretHash`, `plainReducted` |
| WebChatChannel | `web_chat_channel` | same | `id` (caller-supplied PK), `openBotId` (FK → `open_bot`, CASCADE), `name`, `secret1` (indexed), `secret2` (indexed), `createdAt` |

All three use `@Entity()` with no argument, so table names come from TypeORM's
`DefaultNamingStrategy`: snake_cased class name for tables, but **camelCase for implicit
join columns** (`openBotId`, not `open_bot_id`). That inconsistency is TypeORM's, not a
local convention.

### OpenBot

**Source:** `src/entities/openbot.entity.ts` — 6 columns

| Column | Property | TypeORM declaration | Postgres | MySQL | Nullable | Default |
|--------|----------|---------------------|----------|-------|----------|---------|
| `id` | `id` | `@PrimaryGeneratedColumn('uuid')` | `uuid`, PK | `varchar(36)`, PK | no | generated |
| `handle` | `handle` | `@Column()` + `@Index('IDX_OpenBot_handle', { unique: true })` | `varchar` | `varchar(255)` | no | — |
| `endpoint` | `endpoint` | `@Column()` | `varchar` | `varchar(255)` | no | — |
| `schemaVersion` | `schemaVersion` | `@Column({ default: 'v1.3' })` | `varchar` | `varchar(255)` | no | `'v1.3'` |
| `createdAt` | `createdAt` | `@CreateDateColumn()` | `timestamp` | `datetime(6)` | no | now |
| `updatedAt` | `updatedAt` | `@UpdateDateColumn()` | `timestamp` | `datetime(6)` | no | now, on update |

`handle` carries the only named index in the schema, `IDX_OpenBot_handle`, and it is
unique. Handle format is validated in the DTO layer, not the DB:
`/^[a-zA-Z][a-zA-Z0-9-]{2,62}[a-zA-Z0-9]$/`.

`toDto(): OpenBotDto` exposes every field.

### OpenBotSecret

**Source:** `src/entities/openbot.entity.ts` (same file) — 6 columns + FK

| Column | Property | TypeORM declaration | Postgres | MySQL | Nullable |
|--------|----------|---------------------|----------|-------|----------|
| `id` | `id` | `@PrimaryGeneratedColumn('uuid')` | `uuid`, PK | `varchar(36)`, PK | no |
| `openBotId` | `openBot` | `@ManyToOne(() => OpenBot, { onDelete: 'CASCADE' })` `@JoinColumn()` | `uuid` FK → `open_bot(id)` ON DELETE CASCADE | `varchar(36)` FK | yes (TypeORM default for an undecorated `@ManyToOne`) |
| `description` | `description` | `@Column()` | `varchar` | `varchar(255)` | no |
| `createdAt` | `createdAt` | `@CreateDateColumn()` | `timestamp` | `datetime(6)` | no |
| `expiresAt` | `expiresAt` | `@Column({ nullable: true })` typed `Date` | `timestamp` | `datetime` | yes |
| `secretHash` | `secretHash` | `@Column()` | `varchar` | `varchar(255)` | no |
| `plainReducted` | `plainReducted` | `@Column()` | `varchar` | `varchar(255)` | no |

No index on `secretHash`, so validating a presented bot secret is a table scan. That is
tolerable only while the secret count stays small.

`toDto(secret?)` exposes `secretId`, `description`, `createdAt`, `expiresAt`, and `secret`
— the plain value on creation only, `plainReducted` thereafter. `secretHash` is never
returned.

### WebChatChannel

**Source:** `src/entities/webchat.entity.ts` — 5 columns + FK

| Column | Property | TypeORM declaration | Postgres | MySQL | Nullable |
|--------|----------|---------------------|----------|-------|----------|
| `id` | `id` | `@PrimaryColumn()` typed `string` — **caller-supplied, not generated** | `varchar`, PK | `varchar(255)`, PK | no |
| `openBotId` | `openBot` | `@ManyToOne(() => OpenBot, { onDelete: 'CASCADE' })` `@JoinColumn()` | `uuid` FK → `open_bot(id)` ON DELETE CASCADE | `varchar(36)` FK | yes |
| `name` | `name` | `@Column()` | `varchar` | `varchar(255)` | no |
| `secret1` | `secret1` | `@Column()` + `@Index()` (auto-named `IDX_<hash>`) | `varchar` | `varchar(255)` | no |
| `secret2` | `secret2` | `@Column()` + `@Index()` (auto-named `IDX_<hash>`) | `varchar` | `varchar(255)` | no |
| `createdAt` | `createdAt` | `@CreateDateColumn()` | `timestamp` | `datetime(6)` | no |

`secret1` and `secret2` are both independently valid for DirectLine token generation (key
rotation pattern), which is why both are indexed. Neither is unique — nothing at the DB
level prevents two channels sharing a secret.

`toDto(): WebChatChannelDto` exposes `id`, `name`, `createdAt`, `secret1`, `secret2`.

## Enums

No enums, in TypeScript or in SQL. Every column is a scalar string, timestamp, or uuid.

## Runtime / In-Memory Objects (not persisted)

There is no table for conversations or activities — the persisted schema is only the three
tables above.

### Conversation (runtime state)

| Field | Type | Notes |
|-------|------|-------|
| `conversationId` | string | `<12-char-random>-<region>` |
| `token` | JWT string | DirectLine JWT, see below |
| `streamUrl` | string | `ws://<DIRECTLINE_SOCKET_URL>/v3/directline/conversations/:id/stream?watermark=…&t=<token>` |
| `watermark` | integer | Activity counter, held in Redis or in-memory via `AtomicOperationsService`, keyed by `conversationId` |

Conversation state is fully represented by the signed JWT the client holds. Nothing is
written to SQL.

### DirectLine JWT payload (`DirectLineTokenPayload`)

| Field | Type | Notes |
|-------|------|-------|
| `bot` | string | `OpenBot.handle` |
| `site` | string | `WebChatChannel.id` |
| `conv` | string | Conversation id |
| `user` | string (optional) | Supplied at token generate / conversation create |
| `iss` / `aud` | string | `https://<DIRECTLINE_HOST>/` |
| `nbf` / `exp` | number | Unix timestamps; default lifetime 3600s |

### Bot access token payload (OAuth2 client credentials, `/oauth2/v2.0/token`)

Signed with the same `JWT_SECRET`.

| Field | Notes |
|-------|-------|
| `aud` | `scope` param, or `https://api.botframework.com/.default` |
| `iss` | `DIRECTLINE_HOST` |
| `sub` | `client_id` = `OpenBotSecret.id` |
| `exp` | Unix timestamp |

### Activity (runtime, `botframework-schema` types only — a devDependency)

Fields this service sets at creation:

| Field | Value |
|-------|-------|
| `id` | `<conversationId>|<7-digit-zero-padded-counter>`; for `typing`, `<conversationId>|<11-random-chars>` |
| `timestamp` | `new Date()` |
| `serviceUrl` | `DIRECTLINE_HOST` |
| `conversation` | `{ id: conversationId, isGroup: false, conversationType: '', name: '' }` |
| `recipient` | on user activity: `{ id: '<handle>@<siteId>', name: handle }` |
| `replyToId` | set on bot-reply activities |

All other fields (`type`, `text`, `attachments`, `from`) pass through verbatim.

### Pagination wrapper

All list endpoints return `PaginatedTransform<S, T>`: `items` (`T[]`), `total`, `page`
(1-based), `pageSize`.

## Notes

- **This service is live, not planned.** It runs in HBF local dev against MySQL and is
  driver-agnostic by construction. Any documentation describing it as "PostgreSQL only" or
  "planned, not yet in use" is stale — Postgres is the repo default and the standalone
  Docker Compose target, nothing more.
- **`synchronize: true` with zero migrations** — see *Schema Management* above. This is the
  single most important operational fact about this service's data layer.
- `WebChatChannel.id` is caller-supplied. Uniqueness is the caller's responsibility; a
  collision is a PK violation at insert, not a validation error.
- `OpenBotSecret.secretHash` is a SHA-256 hash and is never returned by the API. The plain
  secret is shown exactly once, at creation.
- Both `@ManyToOne` relations omit `nullable: false`, so `openBotId` is nullable in the DB
  on both `open_bot_secret` and `web_chat_channel` despite being conceptually required.
- The watermark counter is keyed by `conversationId` and increments on every non-`typing`
  activity.
